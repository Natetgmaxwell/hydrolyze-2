## Requirements (V0.40_SPEC.md §Slice 4 — per-swimmer zone gate with V0.39 intensity fallback)

The V0.39 gate is a single `setIsAnaerobic` boolean (global, intensity-based). V0.40 makes it **per-swimmer and zone-aware**: when a swimmer has a usable profile and the set's actual rep pace resolves into a zone, the drop rule fires ONLY for **Hard/Sprint** sets. When there's no usable profile (or zone resolution fails), the V0.39 hard/race intensity gate is the fallback — unchanged.

### 4a. Model: per-swimmer zone gate (pure logic, TDD)

Extend `RestCountdownModel` so the gate is resolved **per swimmer at evaluate time**, not globally at construction:

- Keep `setIsAnaerobic` as the FALLBACK (V0.39 behavior — used when no per-swimmer zone is supplied).
- Add an optional per-swimmer zone classifier. The model does NOT know about `SwimmerTestProfile` or the DB — the VM resolves the swimmer's usable profile → `TrainingZones`, then passes a **pure closure/predicate** OR a precomputed per-swimmer decision the model can evaluate. Design it as:
  ```swift
  // A zone decision for a swimmer: whether the drop rule should fire
  // for them based on their zone + the set's pace. The model stores
  // this per-swimmer; evaluate() consults it.
  ```
  The cleanest shape (mirroring how the model already stores `strikes` / `currentExtensionSec` per swimmer):
  - `var zoneGateBySwimmer: [String: ZoneGate] = [:]` where `ZoneGate` is a small enum/struct the VM populates per swimmer. `ZoneGate` should capture: whether the swimmer HAS a usable profile (`hasProfile`), and if so, the pace-to-zone classification of the CURRENT rep. But the model only gets `repTimeMs` + `distanceMeters` in evaluate — so the model CAN compute the rep's per-100m pace (`pace = 100 * 1000 / repTimeMs ... careful: repTimeMs is ms, distanceMeters is m; per-100m pace in s/100m = (repTimeMs/1000) * (100/distanceMeters)`).
  - Given the rep pace (s/100m), classify against the swimmer's zone boundaries. To do this the model needs the boundaries. Pass them in: a per-swimmer `ZoneGate` carrying the four boundary paces (easy/steady/hard/sprint as s/100m) + a `hasProfile` flag. In `evaluate`, when `zoneGateBySwimmer[swimmerId]` exists:
    - `hasProfile == true` → fire only if the rep's pace lands in **Hard or Sprint** (rep pace s/100m <= hard boundary AND >= sprint boundary... define: pace is "faster" (lower seconds) = higher zone. Classify: if pace < hard boundary s/100m → Hard or Sprint. Specifically: if the rep pace (s/100m) is <= hardBoundary → Hard/Sprint → gate OPEN. If pace > hardBoundary (slower, i.e. Easy/Steady) → gate CLOSED → return nil).
    - `hasProfile == false` (or no zoneGate entry) → fall back to `setIsAnaerobic` (V0.39 behavior).
  - **Zone resolution failure never crashes**: if the per-swimmer entry exists but the boundaries are invalid (nil/non-finite), treat as fallback → `setIsAnaerobic`.
- **Signature decision**: you may either (a) keep `setIsAnaerobic` and add a per-swimmer `ZoneGate` dict the VM mutates before evaluate, or (b) pass the gate into `evaluate(...)`. Prefer (a) — a `var` the VM sets alongside `strikes`, consistent with how the model already holds per-swimmer state. Name it clearly. If (b) is cleaner, justify it.

**TDD** — extend `ios-native/Hydrolyze/Tests/CLI/RestCountdownCLITest.swift` (or add a new `TrainingZonesGateCLITest` if it's cleaner — but prefer extending RestCountdownCLITest since it's the same model + same runner; the runner already compiles Prediction + RestCountdownModel). Cover at minimum:
1. Swimmer WITH usable profile, rep pace in Steady zone (slower than hard boundary) → `evaluate` returns nil (gate closed).
2. Same swimmer, rep pace in Hard zone (<= hard boundary) → evaluate returns non-nil.
3. Same swimmer, rep pace in Sprint zone → evaluate returns non-nil.

6. Invalid zone boundaries (non-finite) → falls back to `setIsAnaerobic`, never crashes.
