## Why

A scheduled workout that the coach opens at the wall should read as **a console**, not a document. Today it opens as a workout list (`WorkoutDetailView`) — every fragment is its own decision surface — and the next action ("time this set") is the row's play CTA, not the page's intent. The coach's eyes scan for "what do I tap RIGHT NOW" and the screen offers N equivalent choices. The console reorganises this: one state at a time, one primary CTA per state, and the rest of the workout recedes behind the next rep.

Two design frames hold this together:

- **Rory Sutherland (perception engineering).** Timing is the lazy path if the surface invites it. Joining should feel like joining, not booting. A "👤 14 / squad 14" breadcrumb signals membership, not a checklist. A "Send-off :30" countdown signals the wall is yours, not that you have a task. The psycho-logic matches what the coach sees at the wall: one set on, one set next.
- **Homo economicus (coach attention is the scarce currency).** The app pays for anything data can infer. Roster pre-fill from `AttendanceResolver` is free. Wave order from `WaveAllocator` is free. What the coach cannot infer — "did this swimmer actually turn up?", "is this rep's send-off ready?" — is what the coach spends attention on. One primary action per state. Everything else is decoration.

## Section 1 — Console states & transitions

### PRE
- One screen. The workout title + the set list (read-only, in `WorkoutPreview` or its successor) + the 👤 breadcrumb + one button.
- Tap Start Session → leave PRE; enter LIVE directly at the first timeable rep's `.ready` state.

### LIVE
- Current rep's stopwatch is the one prominent affordance. The rep's data is the only expandable block; the other reps (and the rest of the workout) compress to one-line summaries at the top of the screen.
- LAP fires the stopwatch tap + advances to BETWEEN.
- STOP transitions to BETWEEN with the rep marked complete (the rep summary collapses into the top list).
- Tapping a completed rep does **nothing** (decision 9 + §8). The tap target is the row's data, not a re-launcher.

### BETWEEN
- Send-off countdown (`@ 1:30` → 1:30, 1:29, ..., 0). At :00, fire LAP-equivalent for the next rep's stopwatch and enter LIVE for that rep.
- `Next rep` pill: short-circuits the wait. Non-blocking, exists for cases where the send-off is already past (real-life drift) or the coach wants to override.
- If the current rep is the last in the set, BETWEEN's countdown auto-progresses to POST on :00 instead of next-rep.

### POST
- One rep per line. Names + times. Confidence dots if any rep is unpaired (mirrors `SessionReviewView` row vocabulary — same chip, same colour).
- Two CTAs: `Review pairs` (pushes `SessionReviewView(sessionId:)` for the current session, the existing surface — no rebuild) and `End session` (dismisses to `TodayView`).

### Entry points
- `TodayView`'s `WorkoutCard` Start Session CTA → `SessionConsoleView` (today: pushes `SessionStartView` — replaced).
- `WorkoutsListView` row tap → `SessionConsoleView` (today: pushes `WorkoutDetailView` — replaced for *scheduled* workouts only; builder-state workouts go to `WorkoutDetailView` as today).
- `WorkoutDetailView`'s "Mark Complete" → `SessionConsoleView`'s POST on re-open (the workout is read-only after complete).

## Section 2 — Attendance breadcrumb

👤 icon + count. **NON-INTRUSIVE**. Never gates Start Session (decision 7). Tap → roster sheet for corrections.

### Pre-tick source
Two cases, both consume `AttendanceResolver` directly via `SessionConsoleViewModel.preTickRoster()`:

1. **Habital squad** (≥1 standing slot matches `workout.weekday` + `amPm`). Show all attending via `standingSlot` + `explicitIn`. Source: `CoachIntentService.fetchResolvedAttendance(forWorkoutId:)` — the same path `AttendanceBadge` uses today.
2. **Cold-start squad** (no standing slots). On the first PRE open for this workout, show a quick multi-select sheet with all squad swimmers (`SessionRosterSnapshot`-style) so the coach populates the breadcrumb. The selection writes `SwimmerAttendanceIntent` rows (`source = "coach"`, `intent = "in"|"out"`), which on next open is read as `explicitIn`/`explicitOut`.

### Correction feedback
- Coach correction in roster sheet → `setIntent(swimmerId:intent:)` writes `SwimmerAttendanceIntent` (today's path).
- **Habitual-prior update rule (v1 may be log-only):** 3 consecutive identical overrides for the same `(swimmer, workout.weekday, amPm)` writes a synthetic `SwimmerTrainingSchedule` row. This rebuilds the habitual prior. **V0.54 ships the counter + the log line; the synthetic row write is V0.55** (reasoning: low blast radius for a missing write, high blast radius for a wrong write that the coach can't audit without a smoke test).
- Breadcrumb updates immediately on correction (today: `CoachIntentService.setIntent` already reloads `attendanceEntries`).

### Edge cases
- **Empty squad** (coach has no swimmers yet): breadcrumb reads "👤 0". Start Session stays enabled — pressing it lands in LIVE with `currentRoster = []` (V0.51's solo-swimmer fallback handles 0-roster as `expectedLapCount = nil` + non-fatal, decision §9 risk 5).
- **All swimmers marked out** (squad exists but none attending): breadcrumb reads "👤 0 / N". Start Session still enabled, with a one-line caption "no swimmers marked attending". Coach can override in roster sheet.
- **RLS / network error on fetch**: breadcrumb shows "👤 ?" with a retry tap. Start Session stays enabled (fail-open: the picker never gated Start, neither does the breadcrumb).

## Section 3 — Wave assignment folded into timing flow

WaveAllocator runs at `LIVE.enter()` — the moment the first rep's stopwatch is about to arm — NOT in PRE. This is the spec's "confirm-not-construct" (decision 8):

- The wave preview was always a `WaveAllocator` output + a drag-drop surface. The drag-drop is a coach override for collision. The skip-picker path (V0.49/V0.51) bypassed it by synthesising wave_assignments from the cached roster. The Console brings it back into the LIVE state as a one-tap confirm surface.
- At `LIVE.enter()`: `WaveAllocator.allocate(roster, sets, poolConfig, predictions)` runs. Its output populates `wave_assignments` rows idempotently (V0.51's `synthesizeWaveAssignmentsIfMissing` is the writer; the Console passes it the full computed matrix instead of placeholder rows).
- The first rep's stopwatch entry shows a **waves-by-lane** chip strip (same `Lane` chip from V0.52 `FragmentWaveSheetView`, plus the lane order — `Lane 3 Jack`, `Lane 4 Ariana`). Coach can tap any chip to swap two lanes (a no-drag, single-tap interaction). Tap a lane chip → quick-action menu with the other lanes' names → tap to move. One swap per tap.
- **No separate "Wave Preview" screen** (decision 10). The waves are visible at the moment of first rep's stopwatch entry, not as a blocking screen. The first rep's stopwatch is the primary CTA; the wave chip strip is a one-tap affordance above it.

## Section 5 — Start-Session target

`Start Session` → first timeable rep's `.ready` (zero intermediate screens).

- "First timeable" = the lowest-orderIndex `WorkoutSet` whose `set.distance > 0` AND whose parsed repGroup has at least one fragment with `isTimable == true` (V0.53.1 contract). For non-composite sets, `isTimable = set.intensityType != .easy`.
- If no set is timeable (every set is easy / has no distance / has no fragments), Start Session transitions to POST (decision 6 fallback) — a workout with no timable sets is a "session complete" surface, not a "ready" surface.
- **Rejected for now (decision 10 alt):** one screen earlier — a "Pick first set" picker. Rejected because: (a) it adds friction the data can infer, (b) it makes the screen-state graph wider without value, (c) the first timeable set is the obvious first thing a coach times. Re-open this only if the first timeable heuristic gets wrong picks in practice (V0.55 telemetry).

## Section 8 — Acceptance criteria (per state, testable)

### PRE state
- PRE shows exactly **one** primary CTA (`Start Session`). No other accent-colored button. Verified by snapshot test: `accentAction` foreground appearances ≤ 1 in PRE.
- Attendance breadcrumb requires **zero** taps to proceed. Verified: tap `Start Session` directly without touching the breadcrumb → LIVE enters with the pre-ticked roster.
- The 👤 count matches `CoachIntentService.fetchResolvedAttendance(forWorkoutId:).count`. Verified by stubbing the service to return a known fixture and asserting the breadcrumb text.
- First-timeable rep id matches the spec's heuristic (lowest orderIndex with `distance > 0` and `intensityType != .easy` OR with at least one timable fragment). Verified by fixture-driven unit test on `SessionConsoleViewModel.firstTimeableRepIndex()`.

### LIVE state
- The stopwatch is **the** primary CTA. One coral button (`accentAction` foreground). Other affordances are `textPrimary` / `textMuted`. Snapshot: `accentAction` foreground appearances ≤ 1.
- Completed reps (count > 0) render as collapsed one-line summaries at the top of the LIVE screen. Current rep is the only expanded block. Snapshot: only one `RepCard(mode: .live)` at a time.
- Tapping a completed rep does NOT re-open timing. The tap target is the row's data (`sessioned times row`), not a re-launcher. Verified by simulating tap on a collapsed row in a unit test and asserting no `lapRecorded()` invocation.
- Wave chip strip shows one chip per lane (up to `poolConfig.laneCount`, default 6). Tap a chip → quick-action menu with the other lanes' names. Tap a name → swap the two lanes' wave_assignments rows. Verified by `WaveChipStrip` snapshot + integration test on `SessionConsoleViewModel.swapLanes(a:b:)`.

### BETWEEN state
- Send-off countdown matches the parent set's `intervalText` parsed to milliseconds. Verified by fixture (`@ 1:30` → 90000 ms).
- `Next rep` pill fires `SessionConsoleViewModel.nextRep()` immediately, regardless of remaining countdown. Verified by tapping the pill at countdown :30 → LIVE state at the next rep without :30 wait.
- Between→POST: when current rep is the last in the set, the countdown auto-progresses to POST on :00 instead of next-rep. Verified by setting `currentRepIndex == reps - 1` and letting the countdown hit 0.

### POST state
- One row per rep, in order. Names + times. Confidence dot colour matches `SessionReviewViewModel.rowConfidenceBand` (same vocabulary, same colours).
- Two CTAs: `Review pairs` and `End session`. Exactly one is `accentAction`-coloured (`End session` is primary, `Review pairs` is secondary `bgSunken`). Snapshot: `accentAction` foreground appearances ≤ 1.
- Tapping `End session` dismisses to `TodayView`. Session row in DB is unchanged (no save, no delete — POST is read-only summary; save already happened in `.saving`).
- Unmatched-gap rows render with an inline ⚠ + a tap target. Tapping the row pushes `ReassignSheet` (the existing sheet from `SessionReviewView:64`).

### Cross-state
- `WorkoutPreview` contains zero `Button` with timing action. Verified by static scan: no `Button(action:)` whose body references `lapRecorded()` / `TimingView` / `startSession()`.
- `RepCard(mode: .preview)` contains zero `accentAction` foreground. Snapshot.
- `SessionConsoleViewModel.state` advances `PRE → LIVE → BETWEEN → LIVE → … → POST`. No state is skipped. State machine unit test.

### Cross-route
- `TodayView`'s `WorkoutCard` → `SessionConsoleView`. Verified by removing `showSessionStart = true` codepath and the app still compiles + the tap navigates.
- `WorkoutsListView` row tap → branch on `workout.status`. Verified by fixture (`.scheduled` → `SessionConsoleView`, `.draft` → `WorkoutDetailView`).

## Section 10 — Risks and open questions

### R1. TimingView coupling (1300-line file)
**Risk:** The wrapper-not-rewrite (decision 12) requires adding `mode`, `currentRepIndex`, `currentSetIndex`, `repsByRepIndex` to `TimingView` + `TimingViewModel`. The existing V0.49 sheet coordination + the .saving → review direct-render + the onRecord callback all live in `timingBody`. A naive wrapping (replace the cover with `SessionConsoleView` containing `TimingView`) double-fires some callbacks.

**Plan:** Add the new fields as additive (no existing behaviour change). The Console observes `TimingViewModel.state` via `@StateObject` and translates the timing state into a `ConsoleState` sub-state. Sub-states don't change `TimingViewModel.state` itself — BETWEEN is a derived flag from `(state == .ready || state == .running) && currentRepIndex < reps - 1`.

**Open question:** do we want a single `.ready → .running → .finished` state machine, or do we want BETWEEN as a sibling? **Lean:** sibling, because the countdown timer is a different kind of timer than the stopwatch (different cadences). Spec'd as a sibling.

### R2. Habitual-attendance cold start
**Risk:** `CoachIntentService.fetchResolvedAttendance` returns the *resolved* set (standing slots + explicit intent). For a brand-new squad with zero history, `hasNoSignal == true` and the resolver returns []. The current `SessionStartViewModel.loadRoster` handles `[]` by selecting everyone (fallback caption: "No one's marked their attendance yet — everyone's selected"). The Console breadcrumb can't replicate that without showing "👤 0" + a "Pick attendees" button on first open.

**Plan:** S5 cold-start sheet uses `RosterPickerView` (already exists) and writes `SwimmerAttendanceIntent` rows so the breadcrumb has data on subsequent opens. **First-time UX** (the "everyone's selected" fallback) is NOT preserved in the Console — by design, the breadcrumb is honest about not knowing.

**Open question:** should the Console preserve the "everyone's selected" fallback for the *very first* PRE open of a cold-start squad (showing "👤 all" with a confirmation chip), or render "👤 0" and force the coach to multi-select? **Lean:** "👤 all" + confirmation chip, matching today's UX. Easy to back out.

### R3. Mid-session interruption / resume persistence
**Risk:** No persistence today. If the app backgrounds mid-LIVE, the timing cover dismisses (iOS behaviour for fullScreenCover on backgrounding). The session row exists in DB (V0.49/V0.51 wrote it), but the in-memory `TimingViewModel.laps` + `elapsedMs` is lost. Re-entering the workout re-renders PRE.

**Plan:** S5 persists `(session_id, workout_set_id, current_set_index, current_rep_index, is_running)` to `UserDefaults` on every state change. On Console re-open, `resumeIfNeeded()` checks if the persisted state matches the current workout + a live `wave_assignments` row exists for that `(session_id, workout_set_id)`. If yes, skip PRE → enter LIVE at `current_rep_index`. If no, fall through to PRE.

**Open question:** what if the coach closed the workout from a different device (the laptop dashboard, say) and the persisted state is stale? **Lean:** stale state in `UserDefaults` is overwritten by the next state change. The DB is the source of truth for "did a session happen" — the Console checks DB for `recorded_times` rows for the session before honoring `UserDefaults` resume. If rows exist for the current rep, the live state in DB wins. **Flag this for Nathan's review** — it's a silent-fail surface.

### R4. WaveAllocator input at LIVE.enter()
**Risk:** `WaveAllocator.allocate` needs predictions (`predictions: [workoutSetId: [swimmerId: Prediction]]`). Today's path builds predictions inside `SessionStartViewModel.lockRoster` from `HistoricalTimePredictor`. The Console would need to call the predictor too.

**Plan:** Lift the prediction-building code into a shared service (`WorkoutService.predictForConsole(workoutId:roster:)`) so both paths can call it. The Console's `liveEnter()` calls it once, caches per-set predictions on the VM, and passes them into `WaveAllocator.allocate`.

**Open question:** does `HistoricalTimePredictor` have any state that makes calling it twice (once today, once in the Console) diverge? **Lean:** it's pure-functional on inputs (DB rows + calibration). Should be deterministic. **Verify by reading `HistoricalTimePredictor.predict()` in `S3`.**

### R5. Zero-roster Start Session
**Risk:** A squad with zero swimmers (cold-start, never onboarded) + Start Session → LIVE enters with `currentRoster = []`. Today's flow has no analog (the picker rejects `selectedSwimmerIds.isEmpty`).

**Plan:** S1 spec'd the breadcrumb as "👤 0" + Start Session enabled (decision 7). LIVE enters; the first rep's stopwatch starts without pairing. `wave_assignments` is empty → V0.51's `expectedLapCount = nil` fallback. The stopwatch runs without auto-stop. Coach sees the bare stopwatch + a one-line caption "No swimmers — tap LAP manually".

**Open question:** is "no swimmers" a real use case for Nathan, or is it always a misconfiguration that should be gated? **Lean:** let the coach proceed (they may be warming up the pool or testing). **Flag this for Nathan's review** — could be a V0.55 add (gate Start Session when breadcrumb reads "👤 0").

### R6. Completed-rep tap target
**Risk:** §8 says "tapping a completed rep does nothing". But the row carries data (the rep's time + swimmer name). The tap target might need to be the row's data (open a detail sheet) — V0.50 already has chip-detail behaviour for non-composite sets.

**Plan:** v1 = "tap does nothing" (matches Rory Sutherland's "joining not booting" — the data is visible inline). V0.55 candidate: tap → sheet with per-rep lap count, average, PB-delta. **Flag for Nathan** — this is a "do we want it?" question, not a "is it correct?" question.

### R7. Between-rep countdown edge cases
**Risk:** A set's `intervalText` can be empty (no send-off — coach's choice). BETWEEN's countdown can't fire on :00 from nil.

**Plan:** If `intervalText` is nil or unparseable, BETWEEN auto-progresses immediately (no countdown shown). `Next rep` pill is the only CTA. Log a debug line. **Document** this in the section-1 BETWEEN wireframe as a "no-send-off" variant.

### R8. Wave chip strip on a single-swimmer set
**Risk:** A solo swimmer has 1 wave_assignment row with `lane = 1`. The wave chip strip renders one chip. Tap → empty swap menu.

**Plan:** Hide the wave chip strip when `roster.count == 1`. Match the V0.51 solo-roster fallback's "no wave preview needed" path. Documented in §3.

1. **TodayView's `WorkoutCard` handler target** (today: `showSessionStart = true` → `SessionStartView`). V0.54 replaces with `showConsole = true` → `SessionConsoleView`. But `TodayView`'s body also has `fullScreenCover(item: $activeSession)` rendering `TimingView` directly (TodayView.swift:58-60) — that codepath exists for the post-picker fallback. Does V0.54 delete that, or keep it as a stale fallback for "no Console yet, but timing must work"? **Lean: delete.** The Console subsumes the post-picker path. But TodayView's body line 59 says `TimingView(sessionId:session.workoutSetId)` with no `prefill` — that's the bare-start path, distinct from the console's `prefill` from the first timeable set. **Need to verify whether the bare-start path is reachable in V0.49+** (i.e. does any caller hit it, or is it dead code that V0.52's sheet flow replaced). If reachable, the Console needs an entry for it.

2. **Habitual-prior writeback** (decision 13). The 3-consecutive-identical-override rule writes a `SwimmerTrainingSchedule` row. The schema migration to support this needs verification — does `SwimmerTrainingSchedule` have an `idempotency_key` for safe retry, or does a duplicate insert crash? **Lean: there's a UNIQUE constraint on `(swimmer_id, weekday, amPm)` (per the resolver test fixture pattern). On Conflict → Do Nothing.** Verify in S5 before shipping.

3. **`RepCard.mode: RepCardMode` flag** (decision 9, §4). The current `WorkoutPreview` reads `mode = .preview` by default. The Console's LIVE state passes `.live`. The question is whether the existing `FragmentCTARow` and `PairRepGroupRow` are `mode`-aware enough to honor `.preview = no CTA`. V0.53 + V0.53.1 added `isTimable` and `showPaceBadge` flags — those are the closest precedent. **Need to grep `WorkoutPreview.swift` for any Button whose action is gated only by `isTimeable` and NOT by `mode`.** If a Button is gated only by `isTimeable`, the preview could still render a play icon on a timable fragment — violating the §8 acceptance ("preview contains zero timing Buttons"). Lean: the `mode` flag is additive and the existing gates get a `&& mode != .preview` conjunct.

4. **The `WorkoutsListView:327` branch** (decision 15). Today's `NavigationLink(destination: WorkoutDetailView(...))` is a single-line change to a status-branched version. But `WorkoutDetailView` is also reached from the builder (`WorkoutDetailView.swift:464` `navigationDestination(isPresented: $navigateToBuilder)` for `WorkoutBuilderView`). That route is **from inside `WorkoutDetailView`** — i.e. it's a forward push, not the entry. **Need to confirm: when V0.54 deletes the `WorkoutsListView` → `WorkoutDetailView` entry, does the builder entry still work?** The builder is reached via `WorkoutDetailView`'s "Edit Workout" button — but if the entry is the Console, the "Edit Workout" button lives on the Console's toolbar `⋯` menu, not on `WorkoutDetailView`. So the builder entry from the Console needs to push `WorkoutBuilderView` directly (not via `WorkoutDetailView`). **Lean: yes, the Console's `⋯` menu pushes `WorkoutBuilderView` directly. `WorkoutDetailView`'s builder entry becomes dead code; deleted.**

5. **`SessionConsoleViewModel.liveEnter()` race** (R4). The first call to `WaveAllocator.allocate` for the first set happens during LIVE.enter(), which itself is triggered by `startSession()` in PRE. If the coach double-taps Start Session (V0.51 prevented this with `isLoading`), two `liveEnter()` calls fire. **Lean: V0.51's idempotent `synthesizeWaveAssignmentsIfMissing` prevents the DB double-write, but the `WaveAllocator.allocate` CPU work runs twice.** Cheap, but worth a `Task` debounce in `startSession()` to prevent the double-fire visually.
