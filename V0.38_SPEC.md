# V0.38 — 3MT Mode: the 3-minute all-out test as a first-class session type

**Status:** LOCKED. Owner: build profile. Branch: v2.0.
**Source:** `docs/research/2026-08-15-3mt-drop-rule-zones.md` (530 lines, commit e36c6a7) — read it first. This spec implements Feature 1 of that doc (3MT mode). Drop rule, recovery flywheel, and zones are later slices (V0.39+).

## Why

Eva Piatrikova's 3-minute all-out test (3MT) is the one metabolic test that needs nothing but a stopwatch — no VO2 master, no lactate strips, no Moxy. Hydrolyze IS the stopwatch and knows who's swimming. The product opportunity is everything after the last wall touch: curve math, interpretation, storage, per-swimmer profile. This is the wedge feature — Nathan will use it this week on himself, Jack, and Ariana — and it creates the data (critical speed) that zones and the recovery flywheel consume later.

## The test, in coach terms

Swimmer goes all-out from the first push-off for 3 minutes. Coach taps LAP at every 25m wall touch. The speed curve (speed vs time) has a characteristic shape: **peak → decay → plateau**. Three numbers come out:

| Number | What it is | Coach vocabulary (UI) |
|---|---|---|
| Peak speed | Fastest 25m split | "Top speed" |
| Critical speed (CS) | Mean speed over the final 30s — the plateau | "Threshold pace" |
| D′ (battery) | Area above CS under the curve, in meters | "Battery" (unit: meters) |

Curve shape tells the story: sprinter = big peak + big drop; distance swimmer = small peak, levels off quickly.

**Familiarisation is mandatory** (Piatrikova 2019): most swimmers need 2 trials before the data is usable. Trials 1–2 show the numbers but flag "learning trial — repeat before using for zones."

### Slice 1 — DB migration (additive only)

One migration, `supabase/migrations/YYYYMMDDHHMMSS_3mt_mode.sql`:

```sql
-- 1. Session type on workouts
ALTER TABLE workouts
  ADD COLUMN IF NOT EXISTS session_type text NOT NULL DEFAULT 'training'
    CHECK (session_type IN ('training', '3mt'));

-- 2. Per-swimmer 3MT profile
CREATE TABLE IF NOT EXISTS swimmer_test_profiles (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  swimmer_id      uuid NOT NULL REFERENCES swimmers(id) ON DELETE CASCADE,
  session_id      uuid REFERENCES sessions(id) ON DELETE SET NULL,
  workout_set_id  uuid REFERENCES workout_sets(id) ON DELETE SET NULL,
  stroke          text NOT NULL DEFAULT 'Free',
  pool_length     integer NOT NULL DEFAULT 25,
  test_date       timestamptz NOT NULL DEFAULT now(),
  trial_number    integer NOT NULL DEFAULT 1,
  peak_speed_mps  double precision NOT NULL,
  critical_speed_mps double precision NOT NULL,
  battery_m       double precision NOT NULL,
  quality_flags   jsonb NOT NULL DEFAULT '[]',
  created_at      timestamptz DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_test_profiles_swimmer
  ON swimmer_test_profiles(swimmer_id, stroke, test_date);
```

RLS: same pattern as `swimmer_pbs` (coach sees profiles for their swimmers). No backfill — forward-only.

### Slice 2 — `ThreeMinuteTestAnalyzer` (new pure Swift service)

New file: `ios-native/Hydrolyze/Sources/Services/ThreeMinuteTestAnalyzer.swift`.

Input: `[Lap]` (25m splits with elapsed times) + pool length. Output:
`ThreeMinuteTestResult { peakSpeedMps, criticalSpeedMps, batteryMeters, curveShape: [Double], qualityFlags: [QualityFlag], trialNumber }`.

Math (from the research doc §1.4):
1. vᵢ = 25 / tᵢ for each split
2. Peak speed = max(vᵢ)
3. CS = mean speed of splits whose cumulative time lands in [150s, 180s] (final 1–2 splits; average the last two for smoothing — stopwatch tap error ±0.2–0.5s)
4. Battery = Σᵢ (vᵢ − CS) × tᵢ over splits where vᵢ > CS (discrete integral, meters)
5. Curve shape = the per-split speed array (for the review-surface plot)

Quality flags (the "didn't go all-out" detector, research doc §1.5):
- `.pacedStart` — split 1 slower than split 2 or 3 (didn't go all-out from the push-off)
- `.peakBelowExpected` — peak within ~5% of the swimmer's 25m PB speed (or Layer-2 prediction at 25m); flag if well below
- `.flatCurve` — CS not below peak by a plausible margin (typically 10–20%)
- `.learningTrial(trial: 1)` — trial 1 or 2: show numbers, flag "repeat before using"

Pure function, no DB, no async — same pattern as `WaveAllocator`. Unit-testable in isolation.

Acceptance:
- Unit tests: synthetic sprinter curve (big peak, big drop) → correct peak/CS/battery; synthetic distance curve (small peak, levels off) → correct values; paced-start curve → `.pacedStart` flag; flat curve → `.flatCurve` flag
- Battery is in meters; CS in m/s; peak in m/s

### Slice 3 — Parser: recognize 3MT in workout text

Extend `WorkoutParser` (and the parse-workout edge function's system prompt): recognize "3MT", "3-min all-out", "3 min test" in workout text → emit a set with `intensity_type = '3mt'`, `reps = 1`, `distance = 25` (split distance), `interval_text` absent (continuous 3:00 swim). The workout-level `session_type = '3mt'` is set when the workout's primary set is a 3MT.

Acceptance:
- "3MT" / "3-minute all-out" / "3 min test" in a workout string parses to a 3mt set
- A normal workout (no 3MT text) is unaffected — `session_type` stays 'training'

### Slice 4 — Timing flow: 3MT session

In the timing screen, when the active set is a 3MT set:

1. Roster locked at start (one-mark-per-workout invariant — unchanged)
2. Stopwatch runs 3 minutes continuous (not per-rep). **New UI element:** a 3:00 countdown display alongside the stopwatch (the only countdown in the app today is the stopwatch itself — there is no rest timer)
3. LAP per wall touch — same muscle memory; each touch = 25m split
4. On stop: splits → `ThreeMinuteTestAnalyzer` → result per swimmer
5. Save: `recorded_times` rows (pace_distance = 25, rep_index = split index, intensity = 'race') + `swimmer_test_profiles` row per swimmer

Pairing: reuse `PairingEngine` as-is — the caller supplies predictions built from `HistoricalTimePredictor` at 25m, race intensity. Known v1 limitation (documented in research doc §2.2): if two swimmers touch within ~0.5s of the same wall, the engine may swap identities for that rep — the review surface catches it; a per-swimmer split-sequence constraint is v2.

Acceptance:
- A 3MT session times 3:00 continuous with LAP splits
- Splits pair to swimmers via the existing engine
- On stop, each swimmer gets a `swimmer_test_profiles` row with correct math
- Trial number increments per swimmer per 3MT session

### Slice 5 — Review surface: the three numbers in coach vocabulary

In the session review surface, a 3MT session shows per swimmer:
- The curve (speed vs time, from `curveShape`)
- Three numbers: **Top speed** (m/s or per-100m pace), **Threshold pace** (per-100m pace), **Battery** (meters)
- Quality flags in coach words: "Learning trial — repeat before using for zones" (never "paced start" or "flat curve" jargon)
- One actionable signal per swimmer, color-coded (🟢🟡🔴⚫) — the analytics constraint

Anti-patterns (explicitly avoided):
- No confidence percentages — CS/D′/peak are direct measurements, not probabilities
- No statistical jargon — no "anaerobic capacity", no "area under the curve", no "D′"
- No modal surfaces — inline only

Acceptance:
- Review surface shows the curve + three numbers per swimmer in coach vocabulary
- Learning-trial flag renders as the coach-facing line above
- Battery trend note: "battery is measured the same way every time — watch the trend, not the number" (D′₃MT underestimates time-trial D′ by ~16%; never mix test types)
