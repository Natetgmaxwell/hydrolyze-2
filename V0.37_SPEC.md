# V0.37 — Parse reliability: stop the 5/10 failure rate

**Status:** LOCKED. Owner: build profile. Branch: v2.0.

## Symptom (verified live, 2026-08-13)

10 sequential parse-workout calls to the deployed edge function with the pinned
test workout (full main set, 1221 chars, 9.9K input tokens):

| req | time | HTTP | degraded | path |
|---|---|---|---|---|
| 1 | 20.6s | 200 | True | LLM failed → fallback |
| 2 | 23.6s | 200 | True | LLM failed → fallback |
| 3 | 6.6s | 200 | None | regex fallback (LLM didn't even try — fallthrough) |
| 4 | 24.5s | 200 | True | LLM failed → fallback |
| 5 | 5.5s | 200 | None | regex fallback |
| 6 | 21.4s | 200 | True | LLM failed → fallback |
| 7 | 5.4s | 200 | None | regex fallback |
| 8 | 19.7s | 200 | True | LLM failed → fallback |
| 9 | 21.7s | 200 | True | LLM failed → fallback |
| 10 | 5.2s | 200 | None | regex fallback |

**5/10 LLM attempts fail, 5/10 succeed.** When LLM fails, server returns
`degraded: true, degradedReason: "llm_error"` and the regex fallback's
V0.35-shaped payload. The iOS client decodes the fallback but the device
frequently reports "server pass failed: network connection was lost" — the
20s+ wait is hitting an iOS-side timeout on the long-poll (root cause still
unconfirmed but the user-side symptom is real and the cure is the same: kill
the flakiness).

MiniMax-M3 is the unstable element. The errors are NOT 429s (no rate-limit
reason fired), they're 5xx-or-empty responses from `api.minimax.io`.

## Goal

Drive the failure rate from 50% to <5% with no architectural change.

## Contract

### Slice 1 — Server: one retry on transient LLM failure

In `_llm.ts:223 callMiniMax()`, wrap the `fetch` call in a single retry that
fires on:
- `resp.status >= 500` (5xx from MiniMax)
- `JSON.parse(data.choices[0].message.content)` throws (malformed JSON in `content`)
- `data.choices` is empty or `data.choices[0].message.content` is empty

Do NOT retry on:
- 4xx (auth, bad request — those are deterministic)
- `MINIMAX_API_KEY` missing

Delay: 1s (constant). The retry happens once. If the retry also fails, throw
the same `LLMError` so the existing `parseWithFallback` falls back to regex.

Acceptance:
- 10 sequential calls on the pinned workout → 9+ succeed with `degraded: false`
- No new test flakiness from the 1s wait (worst-case-extra-time = 1s + 1 LLM call)

### Slice 2 — iOS: explicit 30s timeout with clear error

In `WorkoutService.swift:124`, set:
```
request.timeoutInterval = 30
```

This replaces the URLSession default of 60s with a tighter bound that's
still generous (the LLM is 5-25s, regex fallback is <1s). When the server
takes longer than 30s, URLSession throws `NSURLErrorTimedOut (-1001)` — the
caller's catch (`WorkoutBuilderView.parse:509`) surfaces the message
"Server parse failed — using on-device fallback. The request timed out."

The user sees a clear timeout message, not "network connection was lost",
and the sync result is preserved.

Add the same line in `parseWorkout`'s cache-fast-path's check (no change
needed — cache hit is synchronous).

Acceptance:
- iOS parse failures on the 29s+ cold-LLM cases show "timed out" instead of
  "network connection was lost"
- Fast regex-fallback responses (< 1s) unaffected

### Slice 3 — iOS: surface the degraded flag in the preview UI

(V0.36 added the flag plumbing; this slice makes the banner visible.)

In `WorkoutBuilderView.swift` where `WorkoutPreview` is rendered (~line 196
`workout: viewModel.parsedWorkout ?? ParsedWorkout(title: nil, sections: [])`),
add a `degraded: viewModel.parsedWorkout?.degraded` parameter to
`WorkoutPreview` and render an amber banner above the preview when true,
including the `degradedReason` ("The parser hit a rate limit — using a
fallback. [Retry]").

The banner replaces the silent fallback. The retry button triggers the same
`parseWorkout` call (no cache) and updates `parsedWorkout`.

Acceptance:
- When the server returns `degraded: true`, the iOS preview shows a visible
  amber banner with the reason and a working retry button
- When `degraded: false` or absent, no banner renders

## Out of scope

- Async polling model (202 + job id) — mentioned in the V0.36 → V0.37
  discussion, deferred. The 1-retry + tighter timeout is the cheap fix.
- Streamed response — would let the user see progress, but the 95th-percentile
  parse is already < 30s. Revisit if the 1-retry fix proves insufficient.
- MiniMax provider swap — the API IS the bottleneck. Switching providers
  (e.g., Anthropic) would be a different V0.38 conversation.
