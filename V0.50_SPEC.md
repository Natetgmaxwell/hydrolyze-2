# V0.50_SPEC — Solo / non-composite set attribution (fragment_id stamp)

Status: IMPLEMENTED — committed 2026-08-30 on v2.0. Smoke `SoloLapAttributionSmoke.swift` green (4/4). build-verify.sh SHIPS. Live DB back-fix on row `5af2e6f3…` confirms the bucketing rule.
Branch: v2.0 (post-9cdc8a7)

## Problem

A non-composite set (e.g. `8 x 50 Free @ 1:30`) timed via the **set-level play button** on the workout detail page produced a `recorded_times` row with `fragment_id = NULL`. The V0.48 chip renderer (`WorkoutDetailView.loadFragmentTimes`) filters by `where t.fragmentId != nil`, so the row was invisible — the coach saw no chip at all, even when the row carried a valid `paired_swimmer_id`.

Observed live 2026-08-29 (e2e run, Mac Studio, build ae2ee0a):
- Session `e2e329b0…`, workout `24b6fad8…`, set `fc5d1b6f…` (8 x 50 Free, non-composite, `workout_sets.fragments = []`)
- 1 lap timed via TimingView START → LAP → Save (skip-the-picker path, 1 active swimmer in wave)
- Row `5af2e6f3…`: `swimmer_id=NULL, paired_swimmer_id=<set>, fragment_id=NULL, time_ms=33100, confidence=93`
- Consequence: V0.48 workout-detail chips render zero chips for this set; the coach can't see the time at all

## Root cause

`WorkoutDetailView.setRow(_:)` (line 559) built a `SetPrefill` with `fragmentContexts: nil` for non-composite sets. When the user went through the skip-the-picker path (`V0.49 Slice 1`), `TimingView.onAppear` copied that nil into `viewModel.fragmentContexts`, so `save()`'s multi-swimmer `else if let sid = sessionId` branch called `savePairedLaps(..., fragment: nil)` and wrote `fragment_id = NULL` to the DB.

The chip renderer's `where t.fragmentId != nil` filter then dropped the row; the legacy fallback (`if let frags = set.fragments, frags.count == 1`) only handled single-fragment sets and didn't fire here because `frags = []`.

## Decision

**Stamp a synthetic `FragmentContext` on every non-composite set's prefill.**

- `fragmentId = "set_<set.id>"` (namespaced so a future parsed fragment id can never collide)
- All other fields mirror the parent set (distance, intensity, start, suit, gear, descriptor)
- The `set_<setId>` key is the bucketing handle for both the save path (writes `fragment_id`) and the load path (reads into `recordedTimesByFragmentId`)

**Extend `loadFragmentTimes` legacy fallback to non-composite sets.** When `set.fragments` is nil/empty, bucket all NULL-fragment_id rows for that set under the synthetic key. Back-compat: pre-V0.50 rows (which were broken) now render correctly; the fix is idempotent for new rows.

**Add a set-level chip surface** in `setRow`. Mirrors the V0.48 tier logic (1-2 inline chips; 3+ aggregate `N saved`). The aggregate opens the same per-fragment sheet via `onAggregateTap` when wired — this slice ships the inline rendering only, with the aggregate sheet deferred to a follow-up slice once the spec decides whether set-level buckets deserve a sheet of their own.

## Non-goals (deferred)

- Set-level aggregate sheet (3+ rows): spec needs a decision on whether set-level buckets should share the V0.48 sheet or get their own. Folding into V0.50 would scope-creep.
- Migration script for back-fixing existing NULL-fragment_id rows in bulk: doable in one SQL UPDATE if the coach wants to surface legacy orphaned times, but a one-shot command, not part of this fix.
- `swimmer_id = paired_swimmer_id` promotion when wave has 1 swimmer: explicitly out of scope (per user direction — preserve paired path exactly when 2+ swimmers produce pairings).

## Rationale (why this and not "promote paired_swimmer_id when 1 swimmer")

The user's instruction was explicit: preserve the paired path exactly when 2+ swimmers produce pairings. Promoting `paired_swimmer_id → swimmer_id` when wave count == 1 would mean a divergent write semantic for solo vs paired cases — a future `recorded_times` consumer would need a case-aware fallback to decide "is swimmer_id the truth here or do I still have to join paired_swimmer_id?". The synthetic fragment_id path keeps the row schema constant: every chip-renderer query already reads `paired_swimmer_id`, and the join survives whether the wave had 1 or N swimmers. The chip's name prefix changes only because of the bucket key, not the schema semantics.
