## Why

The stopwatch spine (V0.35–V0.42) makes the app a capture device. The Data Center makes it a *coaching* device: "the coach feels like they are levitating in terms of the amount of coaching insights they are receiving — all without the working memory overload" (user, 2026-06-23). The 0.5-second glance test: "The analytics view must answer the coach's question in 0.5 seconds, or it's noise."

## The proposed v1 signal (from the squad-level progression design, user-approved shape)

Per swimmer, one row, one signal, one color, one label — computed from existing + V0.40/V0.42 data:

| Signal | Meaning | Color | Coach action |
|---|---|---|---|
| "Race ready at 50 Free" | gap-to-PB < 2% at form event | 🟢 | pick for the meet |
| "Building at 50 Free" | gap 2–5%, improving trend | 🟡 | leave alone |

## Contract (v2 — updated per 2026-08-18 decisions)

### Slice 1 — Gear capture (two parts, per Q4 corrected 2026-08-18)

**Part A — Persistence gap-close (dispatched as V0.43a):** the parser extracts fragment gear (V0.37), the preview shows it, the prediction key uses it — but the save path drops it: `TimingService.savePairedLaps` takes no `gear` parameter; `PairedLapRow` has no `gear` field; `TimingViewModel.swift:1199` hardcodes `"none"`. Result: `recorded_times.gear` = 'none' for all 432 live rows despite the parser working. Fix: `savePairedLaps` gains `gear: String?`, `PairedLapRow` gains `gear`, save path passes `fragment.gear.first` (or set gear) at all insert call sites incl. the `skipPairing` raw insert (~line 917).

**Part B — F-V gear selector (new, per Nathan's correction):** one-tap inline chip row in the set-transition gap on the timing screen — None / Paddles / Pull buoy / Fins / Parachute (5 options), prefilled from parsed gear. Stamps every `recorded_time` of the set (same column Part A fixes). The F-V map's x-axis needs resistance tags even when the workout text never names gear. No modal; set-level, never per-rep. Ships in the full V0.43 (after the chain), not in V0.43a.

### Slice 2 — Swimmer settings surface (NEW per Q1)
The swimmer-side ProfileTab gains a real settings surface: form stroke (their event) + preferred gear. Same two fields the coach can already set (`swimmers.form_stroke`, `swimmers.preferred_gear`) — swimmer edits their own, coach overrides from `SwimmerDetailView` (exists). Precedence rule: coach-set value wins until the swimmer changes it themselves (the standing-schedule precedence chain pattern — a write from either side just updates the row).

### Slice 3 — Signal computation (pure Swift service)
`SquadSignalService`: per swimmer, per form event (form_stroke + best-PB distance at that stroke, fallback 50 Free), compute gap-to-PB + trend from recorded_times (last 8 weeks), consume zones (V0.40) for "which zone are they training in" context, recovery signature (V0.42) for the detail row. Output: `SquadSignal { swimmerId, event, signal: .raceReady/.building/.offPace/.quiet, gapPercent, trendSlope }`. Unit-testable.

### Slice 4 — Squad view UI
New surface leading AnalyticsTabView (squad signals first, bands below — Q3): one row per swimmer, color dot + signal label + event, tap → existing SwimmerAnalyticsView. 0.5-second glance: name + color + 3-4 words. Never a number in the headline.

### v1.1 (follow-up, ships after 4+ weeks of gear data — Q5)
F-v squad map: scatter, x = gear (categorical resistance ordinal), y = per-100m pace at form event. Squad median + spread bands. Tap → swimmer analytics. Renders only once gear data exists (hidden otherwise).
