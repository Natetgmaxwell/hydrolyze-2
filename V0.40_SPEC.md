# V0.40 — Zones: per-swimmer training zones from 3MT critical speed

**Status:** LOCKED. Owner: build profile. Branch: v2.0.
**Source:** `docs/research/2026-08-15-3mt-drop-rule-zones.md` §5 (approved 2026-08-15). This spec implements Feature 4 of that doc (zones), scoped to derivation + display + drop-rule gating. Zone-term set writing ("8×100 Steady on 1:30") is **deferred to V0.41** — it changes the parser contract (per-swimmer pace resolution at timing time, not parse time) and deserves its own spec.
**Grounding verified 2026-08-18:** 3MT save/read path exists (`ThreeMinuteTestSaveSupport`, `ThreeMTReviewSupport`, `ThreeMTPanelView`, `swimmer_test_profiles` shipped V0.38). `AnalyticsService` exists (training bands + gear breakdown). **No zone code anywhere.** No squad-level analytics view exists yet (only design originals in gbrain) — per-swimmer display goes on the surfaces that exist: swimmer detail + 3MT review panel. The squad "one signal per swimmer" view is the VISION.md Phase 2 Data Center; documented follow-up, not this spec.

## Why

The 3MT gives critical speed (CS) — the second threshold. Piatrikova's zone model derives the other boundaries as constants of CS: **Easy < 0.89×CS, Steady 0.89–1.0×CS, Hard 1.0–1.035×CS, Sprint > 1.035×CS**. Once a swimmer has a usable profile (trial ≥ 2), every set they swim can be labelled by zone, and the drop rule (V0.39) becomes zone-aware: individualized rest fires on Hard/Sprint sets, not Easy/Steady. This is the "no more than four zones" democratization — club coaches get individualised training zones from nothing but a stopwatch.

## Contract

### Slice 1 — `TrainingZoneService` (new pure Swift service)

New file: `ios-native/Hydrolyze/Sources/Services/TrainingZoneService.swift`. Same pattern as `ThreeMinuteTestAnalyzer`: pure, no DB, unit-testable.

Input: `ThreeMinuteTestResult` (or the profile's `criticalSpeedMps` + `peakSpeedMps`). Output:
`TrainingZones { easy: PacePer100m, steady: PacePer100m, hard: PacePer100m, sprint: PacePer100m, criticalSpeedMps, sourceTrialNumber }`.

Math (research doc §5.1, approved):
- Boundaries: 0.89 × CS (Easy/Steady), CS (Steady/Hard), 1.035 × CS (Hard/Sprint). Peak speed = top of Sprint.
- Paces per 100m: `pace = 100 / (boundary_mps * 60)` → mm:ss per 100m, e.g. "1:12/100m".
- Derived at read time — never stored (the CS/profile is the single source of truth).
- Zone names in coach vocabulary: Easy / Steady / Hard / Sprint — never "zone 1–4" in UI copy.

Acceptance:
- Unit tests: a 1.33 m/s CS → boundaries 1.184/1.33/1.377 m/s; per-100m paces render as mm:ss; peak speed ≥ 1.035×CS means the swimmer reaches Sprint.

### Slice 2 — Persist + load: usable-profile resolution

`swimmer_test_profiles` already stores CS/peak/trial (V0.38). Add the resolution rule:

- **Usable profile = latest profile per (swimmer, stroke) with `trial_number >= 2` and no `learningTrial` quality flag.** Trials 1–2 are flagged learning (research doc §1.5.4) — zones from a learning trial are hidden, with the coach-facing line: "Needs one more test before zones are set" (never jargon).
- `TrainingZoneService` gains a static resolver: `latestUsableProfile(profiles: [TestProfile]) -> TestProfile?` — pure, unit-testable.

Acceptance:
- Resolver returns nil for a swimmer with only trial 1; returns the trial-2 profile when it exists; prefers the newest usable trial.

### Slice 3 — Display: zones on the swimmer detail + 3MT review panel

Two existing surfaces, both per-swimmer (no new squad view — Phase 2 follow-up):

1. **3MT review panel** (`ThreeMTPanelView`): under the three numbers, show the four zone paces in coach vocabulary — "Steady: 1:12/100m" etc. Learning trial → the "repeat before using" line already shown; zones section hidden.
2. **Swimmer detail** (SwimmerDetailViewModel/View): a zones section when a usable profile exists. One glanceable line per zone: name + pace per 100m. Tap for detail deferred.

Anti-patterns (explicitly avoided):
- No "zones 1–4", no "LT/CS/vVO₂max", no confidence percentages — coach vocabulary only (Easy/Steady/Hard/Sprint)
- No new modal surfaces — inline sections
- Zones never implied to exist when no usable profile — hidden, not greyed out

Acceptance:
- Simulator: swimmer with a trial-2+ 3MT profile shows four zone paces on the review panel and swimmer detail; trial-1 swimmer shows neither, with the learning-trial line intact.

### Slice 4 — Zone-aware drop-rule gate (refines V0.39)

In the V0.39 drop-rule evaluation: when the swimmer has a usable profile and the set's target pace resolves into a zone, fire the drop rule only for **Hard/Sprint** sets. Fallback when no usable profile: the V0.39 hard/race intensity gate (unchanged). The zone lookup replaces the intensity gate per swimmer, not globally — a squad where half have profiles gets per-swimmer gating.

Acceptance:
- Swimmer with usable profile: Steady set → no drop-rule evaluation; Hard set → evaluated.
- Swimmer without usable profile: hard/race intensity gate unchanged (V0.39 behavior).
- Zone resolution failure (unparseable pace, no profile) → falls back to the intensity gate, never crashes the evaluation.
