# V0.51_SPEC — skip-the-picker sessions must write wave_assignments + auto-stop + save

Status: SHIPPING on v2.0 — blocks Wednesday pool. Block 1 + 2 in source; 3 verified live.
Branch: v2.0 (post-602c88e)

## Problem

Coach Nathan's live session `846f755e-e512-4b4f-87a2-f94a331cd804`
(workout `e4fb14b4-f43f-48cc-8439-6d81edba784c` "18/08/26 Wed Fitness",
set `c16696b8…` 2x150 Free, 3 fragments, roster = [Ariana Carter `92d9e113…`])
was unrecoverable on device 2026-08-30. Three confirmed DB facts via
Management API:

| Table | Rows for this session |
|---|---|
| `sessions` | 1 (started 09:50:16+00) |
| `session_roster` | 1 (Ariana) |
| `wave_assignments` | **0** ← key |
| `recorded_times` | **0** ← session was never saved |

The watch was kept running past the final rep (no auto-stop fired). Manual
STOP surfaced "No wave assignments for this set. Did the session start
correctly?" — same hard error on RETRY. The session was orphaned.

## Root cause (verified in source, all on canonical tracked files)

The V0.49 S1 commit `a4ff1f1` (2026-08-22, "Roster lookup +
skip-the-picker + Edit Attendees") added two skip branches in
`WorkoutDetailView.swift`:

- `setRow` button → line 660: `if let roster = viewModel.latestRosterSnapshot { activeSession = ActiveSession(id: roster.sessionId, …) }`
- `launchFragmentTiming` → line 876: same pattern

When `latestRosterSnapshot` is non-nil (any workout that previously ran
through the picker and saved a session_roster row), the View sets
`activeSession` **directly** and never opens `SessionStartView`. The
ONLY code path that writes `wave_assignments` is
`SessionStartViewModel.startSession()` (line 647, `upsert(assignmentsPayload)`)
at line ~700 of `SessionStartViewModel.swift`. Skip-the-picker bypasses
it entirely. Three downstream failures then compound:

1. **`loadSessionContext(sessionId:)` (TimingViewModel.swift:1639)** counts
   DISTINCT `swimmer_id` in `wave_assignments`. With 0 rows, the count
   is 0 and `expectedLapCount` stays `nil` (line 1657 only writes when
   `count > 0`).

2. **`lap()` auto-stop (TimingViewModel.swift:818–821)**:
   `if !is3MTSession, let limit = expectedLapCount, laps.count >= limit { stop() }`
   — nil limit → no auto-stop. Coach has to hit STOP manually.

3. **`save()` hard error (TimingViewModel.swift:1181–1186)**:
   `guard !waveAssignments.isEmpty else { errorMessage = "No wave
   assignments for this set…"; return }`. Even manual STOP cannot
   recover — the session is unrecoverable.

The live session 846f755e is in state #3: the session row + roster row
exist (the snapshot would be non-nil on the next workout detail open),
but wave_assignments is empty, so the next skip-the-picker launch would
repeat the bug. The session is one coach action away from being stuck
forever.

## Decision

Fix at three layers (a/b/c) and back-fill the orphaned session (d).
Do NOT remove the skip-the-picker flow — it's the right UX (V0.49 S2
added the roster strip; coaches rely on it). Fix it so the skip
**synthesizes the wave_assignments** it needs to function.

### (a) Skip path must write wave_assignments idempotently

In `WorkoutDetailView.swift` lines 660 and 876, after setting
`activeSession`, **before** the `.fullScreenCover(item:)` body actually
opens (i.e., in the same Task), upsert one `wave_assignments` row per
`(snapshot.entries.count × set)` row using the same shape
`SessionStartViewModel.startSession()` writes. lane=1, position=1,
wave_number=1, predicted_touch_ms=rough estimate (150-free ≈ 150 000 ms
or, when a per-set swimmer PB exists, the PB), send_off_offset_ms=0.
`coach_id` from `authManager.coachId` (nil-safe → empty string,
matching the existing pattern).

Idempotency gate: query `wave_assignments` for `(session_id, workout_set_id)`
before upserting — if any row already exists for this set, skip the
insert. This handles re-entry (coach taps the same set again on the
same day) and recovers the orphaned session 846f755e next time it's
opened (auto-back-fill on first skip re-launch).

The upsert uses Supabase's `onConflict: session_id,swimmer_id,workout_set_id`
so duplicate-tap races collapse to a single row. No second picker
round-trip; no observable UX change.

### (b) `loadSessionContext` solo-roster fallback

After the wave_assignments query (TimingViewModel.swift:1639), if the
result is empty AND `currentRoster.count == 1` AND the prefill carries
`reps`, set `expectedLapCount = reps`. A solo swimmer's set has
exactly `reps` timed laps — the auto-stop gate is unambiguous. Anything
else (0 reps, multi-swimmer roster, no roster at all) keeps the
current behaviour (`expectedLapCount = nil`).

Defended in source: a multi-swimmer session with empty
wave_assignments is genuinely misconfigured — falling back to `reps`
for a 4×100 with 0 wave_assignments would auto-stop after 4 laps when
the coach needs 16. The guard is `currentRoster.count == 1` for that
reason.

### (c) `save()` solo-swimmer paired fallback

`save()` (TimingViewModel.swift:1181–1186) currently hard-errors on
empty wave_assignments. Refactor to:

- If `currentRoster.count == 1` AND wave_assignments is empty, route
  to the single-swimmer branch (the same one `selectedSwimmerId != nil`
  uses) but with `swimmerId` taken from `currentRoster[0]` and
  `paired_swimmer_id = swimmerId` on the resulting `recorded_times`
  row. This satisfies the V0.50 spec rule: a solo swimmer's saved row
  carries `paired_swimmer_id` for chip-renderer join consistency.
- All other cases (multi-swimmer roster + empty wave_assignments)
  keep the hard error. That case is a real misconfiguration (a coach
  has > 1 swimmer picked but no pairing rows), and a silent
  per-swimmer fallback would be wrong.

Concretely: lift `selectedSwimmerId`-fallback through a new helper
`currentSoloSwimmerId() -> String?` that returns the roster singleton
when `currentRoster.count == 1` and `selectedSwimmerId` is nil. The
single-swimmer branch already handles the rest (TimingViewModel.swift:1049).

### (d) Back-fill Nathan's stuck session 846f755e

One Management API insert. Set `predicted_touch_ms = 150000` (150 free,
solo swimmer, no PB recorded), lane=1, position_in_lane=1,
wave_number=1, send_off_offset_ms=0, coach_id = `9b72e5d7…` (read from
the session row). The post-fix `save()` will then succeed on the next
launch of this set in this workout (the skip path's idempotency gate
detects the existing row and skips the insert; `loadSessionContext`
finds 1 row → expectedLapCount = 1 → since `reps = 2`, the auto-stop
won't fire until we hit reps=1, which is still wrong — see override
below).

Override for 846f755e specifically: this set's `reps = 2`, so the
fallback `expectedLapCount = reps = 2` would be right. With the back-fill
of 1 wave_assignments row, `expectedLapCount = uniqueSwimmerIds.count = 1`,
which would under-stop. **Resolution**: the (b) fallback takes priority
when `reps > uniqueSwimmerIds.count` (the swimmer needs to do more reps
than there are swimmers), so `expectedLapCount = max(uniqueSwimmerIds.count,
reps)`. That's a one-line tweak in `loadSessionContext`. Updates the
spec to include this guard.

## Rationale (why synthesize, not route through picker)

- Synthesizing adds 1 upsert call to the skip path, no picker
  round-trip, no observable UX change. Coach still sees the roster
  strip (V0.49 S2).
- Routing through the picker defeats the skip — that's the whole UX
  win V0.49 shipped.
- A "real" wave allocation for a solo set adds zero pairing value (no
  pairing possible with 1 swimmer). The synthesized row's predicted
  touch exists purely so `loadSessionContext` + `save()` find 1 row.
- The idempotency gate makes every tap safe — re-entry on the same
  set on the same day is a no-op.

## Risk + reversibility

- A solo swimmer's saved row has `paired_swimmer_id = soloSwimmer`
  (not `swimmer_id = soloSwimmer`). This is consistent with V0.50's
  explicit rule: "preserve the paired path exactly when 2+ swimmers
  produce pairings". Chip renderers already read `paired_swimmer_id`.
- The synthesized `predicted_touch_ms = 150000` is a fallback when no
  PB exists; PBService will overwrite it on the next session that
  runs through the picker. No persistent damage.
- If the V0.49 S2 Edit Attendees flow nukes the roster mid-session,
  the snapshot is invalidated and the next tap falls through to
  `showSessionStart = true` (the picker). No regression.
