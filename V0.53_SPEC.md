## Diagnosis (parser vs UI)

### Parser output — CORRECT

Live curl against `https://flidjtldfvrrntzwtnsq.supabase.co/functions/v1/parse-workout`
with payload `{"workoutText": "50/100\n3 rounds\n4 × 100 @ 80–85%\n200 easy\n4 × 50 @ 1:00\n25 event rhythm / 25 easy"}`:

```
RG: reps=4 dist=50 interval='1:00' frags=2
  frag: dist=25 intensity={type:'race_pace', label:'event rhythm'} rest_after=None
  frag: dist=25 intensity={type:'easy',       label:'easy'}           rest_after=None
```

The parser correctly:
- Captured the parent rep as `4 × 50 @ 1:00` (reps=4, distance=50, interval captured)
- Attached the slash-form line as TWO fragments whose distances sum to 50
- Set `rest_after: null` on both fragments → the data-model signal for
  "continuous" (no rest between the 25 event rhythm and the 25 easy)

### UI rendering — UNCLEAR (the bottleneck)

`PairRepGroupRow` previously rendered:

```
4 ×                              ← header buried the 50m
· 2 fragments per rep            ← technical jargon
[ 25m @ event rhythm · @ 1:00 ]  ← looks like a swim in itself
[ 25m @ easy · @ 1:00 ]          ← looks like a swim in itself
```

A coach/parent reads "25m event rhythm" + "25m easy" with no visual cue that
these are ONE 50m rep done without rest. They look like two independent 25s.

## Fix (this slice)

### 1. Add `restAfter: Int?` to ParsedFragment

The parser has emitted `rest_after` on fragments since pre-V0.37 (parser
`Fragment` interface, line 86). iOS never decoded it. Without it, the UI
can't tell "continuous" (the 25+25/50 case) apart from "with rest between"
(e.g. `4 x (50 build / :15 rest / 50 easy)`).

Decoded as `Int?` via `decodeIfPresent` so older server versions that don't
emit `rest_after` don't fail decode. nil = continuous (the conservative
default — fragments always belonged to a single rep; restAfter was additive).

### 2. Rewrite PairRepGroupRow header + composite breakdown

**Before:**
```
4 ×
· 2 fragments per rep
[ row 1 ]
[ row 2 ]
```

**After:**
```
4 × 50m
each as: 25 event rhythm + 25 easy — continuous
[ row 1 ]
[ row 2 ]
```

When a fragment carries `restAfter > 0`, the inter-fragment annotation
renders "+ :NN rest" between the affected rows AND the parent breakdown
ends in "with rest between" instead of "continuous". The breakdown uses
`fragment.distance` + `fragment.intensity.label` (falling back to
`intensityLabel`, `descriptor`, `instruction`, "swim") to label each part.

The header still uses the amber divider bar + `4×` prefix; the parent
distance + stroke now render inline so the 50 is the headline the coach
reads first, with the 25+25 breakdown below as the explicit "this is one
rep" signal.

Accessibility: the breakdown row exposes an `.accessibilityLabel` of
"Each rep as 25 event rhythm plus 25 easy" (the "continuous" tail is
redundant for VoiceOver and would double up).

### 3. Forward parent distance + stroke from the call site

`RepGroupRowView` (line 379) now passes `rg.distance` + `rg.stroke` into
`PairRepGroupRow`. These were already available on the rep group but not
forwarded.

## Future-work note — touch_type for fragment times (NOT in scope this slice)

### Rationale (from Nathan's dictated message)

> "the 25 event rhythm fragment should have the capacity to assign a time
> to that 25, and since it's done as a 50, the time is expected to be a
> feet on wall time rather than a hand touch. The distinction between a
> hand touch and a feet on wall touch will be important later when we are
> building out the dashboard for hydrolyze as we want to compare feet on
> wall times to feet on wall times. We don't really want to be comparing
> a finish to the hand to a finish from the feet because one includes the
> turn time and one does not."

### Why deferred

Adding `touch_type` ripples into:
1. iOS `WorkoutSetFragment` model (add `touchType: TouchType?`)
2. iOS `FragmentTimeRecord` model (record which touch the swimmer hit)
3. iOS stopwatch UI (button to choose "hand" vs "feet" at STOP)
4. DB migration adding `touch_type` column to `recorded_times`
5. Supabase Edge Function schema mirror + write path
6. Parser emit (probably auto-derived: composite-rep total time = feet-on-wall
   by construction; single-fragment time = hand-touch by construction; but
   coach needs the override path)

That's a multi-file, multi-system slice. The user's explicit constraint
this slice was "we're just trying to nail down and perfect the parser
interface" — i.e. the parser/UI round-trip is the work, not the
data-model expansion.

### Spec when we get to it (V0.54 candidate)

```
enum TouchType: String, Codable {
    case handTouch      // stopwatch STOP when hand hits wall
    case feetOnWall     // stopwatch STOP when feet hit wall (turn or finish)
    case unknown        // legacy / undecided
}

// on WorkoutSetFragment: optional, parser default for the fragment context:
//   - composite-rep last fragment: defaults to .feetOnWall (finish includes turn)
//   - composite-rep non-last fragment: defaults to .handTouch (mid-rep touch)
//   - single-fragment rep: defaults to .handTouch
// coach can override before STOP.

// on FragmentTimeRecord: required. If .unknown at write time, refuse to save
// until coach picks one. Dashboard comparison key: (touchType == .feetOnWall).
```

Auto-default logic lives in the iOS timing launch path (when the
stopwatch pre-fills from fragment metadata). NOT in the parser — the
parser doesn't know the swimmer's hand vs feet convention.

### Sign-off gate

This needs explicit approval before any code lands because it touches the
DB schema + the timing model. Surface as a one-line tradeoff block when
ready: "Add touch_type to fragment times? Ripples: model + DB + stopwatch
UI + parser-default heuristic. Dashboard comparison depends on it."
